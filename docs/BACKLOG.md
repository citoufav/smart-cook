## B-1 · 多套库存（不同地点各存一份）⬜

**日期**：2026-10-29 ｜ **来源**：用户实际使用后发现

**现状**：全应用只有一套食材/调料数据（`@v1:inventory:ingredients` / `@v1:inventory:seasonings`），跨设备、跨地点都不共享，也无法在设备上切换。

**用户原话**：*"有时候我要在不同地方做菜，库存不通用，虽然绝大多数场景一个都够用，但只能存一套库存还是有点不方便。"*

**两个可能的需求方向（未确认，做之前先问）**：

1. **单机上多套库存档案**——比如「家里」「宿舍」「办公室」，切换后做菜只用当前那套。纯本地，无需后端。
2. **多设备之间同步**——电脑和手机看到同一份库存。这个本质上要一个后端或云存储，跟项目「无后端、BYOK」的定位冲突，成本高一个数量级。

用户描述更像 1，但"不通用"也可能指 2。**先确认再动手。**

**若按方向 1 实现（最省力路径）**：

- 存储层加 profile 维度：`@v1:inventory:profiles`（档案列表）+ `@v1:inventory:currentProfile`（当前档案 id），食材/调料 key 变 `@v1:inventory:<profileId>:ingredients`。
- 改动集中在 `src/services/ingredientService.ts`、`seasoningService.ts`（读写时拼 profileId）、`src/constants/storageKeys.ts`、`InventoryContext`（切换后要重新 `loadData`）。
- UI：设置抽屉里加一个档案选择器（复用现有的 `DropdownSelector`）。
- 迁移：老数据归入名为「默认」的第一个档案，首次读取时自动建。
- 预估 100~150 行。

**顺带一个相关但不同的东西**：Expo Go 里跑的实例和手机上的正式版 APK 数据**天然不共享**（Expo Go 有自己的沙盒）。这不是 B-1 的问题，是调试方式的副作用，别混为一谈。

## B-2 · 开屏引导选完的食材没有重量 ⬜

**日期**：2026-10-29 ｜ **来源**：实现开屏页时自己记的

### P3 · 生成时勾选（约 300 行）⬜

```
选人数/热量/餐类 → [可选] 从菜品库勾 2 道
  → 本地按 basePersonCount 缩放到新人数（复用 applyEdits 的缩放）
  → 差额 = 目标热量 − 已选热量
  → AI 只生成补足的那 1~2 道（复用 generateOneDishStream，把剩余热量写进 instruction）
  → 合并（applyEdits 的 add_dish）+ 重算营养/缺料/采购
  → 进变更预览面板，还能再调
```

**热量要诚实**：AI 估热量误差 ±20%，不做"精确凑到 700 卡"，只把数字摆出来（目标 2100 / 已选 1200 / 新增约 880 / 合计 2080）。

**零件基本齐了**：`applyEdits` 能 add_dish、能按比例缩放、能重算派生字段；`generateOneDishStream` 能单独产一道菜。P3 主要是拼装 + UI。

**两个已知取舍**：

- **`basePersonCount` 存"最近一次"**：同一道菜做过 2 人份又做过 4 人份，存后者。所以"做过 3 次"是准的，但克重是最近那版
- **跨菜顺序**：存的菜自带备菜/炒制步骤（单做那道菜时可用）；组合成菜单时需要重排顺序，暂定按勾选顺序，不调 AI

# 路线图（R-*）

远期功能与它们对现有代码的要求。**只记需求与影响面，不预先写代码**——真正做的时候按当时的代码再定实现。顺序大致按「无后端 → 有后端」排。

## R-1 · 多语言系统（i18n）⬜

**现状**：零预留。72 个源文件里 46 个含中文，约 580 行（含注释，纯 UI 文案粗估 300~400 条），全部硬编码在 JSX 里。

**三处要改，难度递增**：

1. **UI 文案**——抽 `t()` + 语言包。工作量在这块（46 个文件），但机械。
2. **AI 输出语言**——`aiService.ts:216` 的 `18. 所有输出使用中文` 写死在 system prompt 里。改成变参。
3. **prompt 骨架**——`SYSTEM_PROMPT_CN` 整段是中文，且含中餐专属规则（`中餐为主，1人份主料150-300g`）。要按语言拆模板。

**语言存哪**：`UserPreferences.locale` —— **字段已于 2026-10-30 预留，值是 `'zh-CN'`**，目前无人读取。

**注意**：语言和服务端无关，纯前端就能做完。但语言包里的菜名、调料名会被写进库存和 AI 输出，**切换语言后已有数据不会翻译**——要么接受混合，要么只对新数据生效。这点先想清楚再动手。

## R-2 · 多国家菜系支持 ⬜

**现状**：`SYSTEM_PROMPT_CN` 第 10 条写死中餐；`tastePreferences: string[]` 是自由字符串（开屏页选的川菜/清淡之类），AI 按字符串理解，没有菜系 id 概念。

**要引入一个 `cuisine` 维度**：菜系 id + 显示名 + prompt 片段 + **单位体系**。

单位是坑：克重在中餐里通用，但西餐写 `cup`/`oz`、日料写 `大さじ`。这不只是换算，是表达习惯——硬转成克会让菜谱读起来别扭。`buildStage1UserPrompt` 里的「克」和系统 prompt 里的「Xg」格式都要跟着菜系走。

**和 R-1 是同一处改动**：`UserPreferences.cuisineIds: string[]`（**2026-10-30 已预留，目前恒为空**），prompt 模板化时一起做。分开做两次是浪费。

## R-4 · 图片识别食材记录 ⬜

**要什么**：

**对架构无要求**：纯新增一个 service 函数 + 一个页面，不挡路。放后台做。

## R-5 · 食物过期提醒 ⬜

**现状**：`Ingredient` 只有 `createDate`。AI 是靠「已存放 N 天」（`aiService.ts:232`）自己猜新鲜度的，没有保质期概念。

**要什么**：

1. `Ingredient.expireDate?: string`（**2026-10-30 已加进类型和 service，暂无 UI**）
2. **品类 → 默认保质期映射**：肉 3 天 / 叶菜 5 天 / 蛋 21 天 / 冷冻 90 天。这个表要能调，不同存储条件（冷藏/冷冻/常温）差别很大
3. `expo-notifications` 本地通知 + 通知权限
4. 库存页的临期排序/标红

**这是唯一一个「现在加字段比以后加便宜」的功能**：一旦用户有一批没 `expireDate` 的数据，补录要一条条填。字段现在加、UI 以后做，成本是 0。

## R-6 · 云端账户同步（食材 + 记录）⬜

**现状**：10 个存储 key 全是扁平的 `@v1:xxx`（`src/constants/storageKeys.ts`），没有 userId 概念。「这台设备的数据」这个假设渗透在全部读写路径里。

**为什么最难**：不是「换个存储后端」，而是引入**「两份数据可能不一致」这个新状态**，然后要回答：

- 两台设备同时改库存，谁赢？（last-write-wins 会丢数据，CRDT 要重构整个数据模型）
- 离线改了，上线后怎么合？
- 删除怎么传播？（没有墓碑的同步会把删掉的食材「复活」）

**预留缝**：存储 key 加命名空间 `@v1:u:<userId>:inventory:ingredients`。**改起来只在 `storageKeys.ts` 一个文件**，但错过就要写数据迁移。

**判断**：现在**不改**。等 R-6 真做时一起改，届时用户量小（可能就你自己），迁移成本≈0。记在这里是因为「改法只有一种」，别忘了。

**和 B-1 的关系**：B-1（多套库存）和本地多档案是同一层命名空间问题，做 B-1 时顺手设计，别做两遍。

## R-7 · 会员 ⬜

**现状**：无账号、无支付、无后端。

**链条**：账号 → 订阅状态 → 额度（AI 调用次数 / 图片识别次数）→ 支付（App Store / Play 内购，抽成 15~30%）。

**硬前提是 R-3**：没有云端代理就没有可计量的「用量」，会员没东西可卖。所以 R-7 必然排在 R-3 之后。

**注意应用商店规则**：iOS 上卖数字服务必须走内购（不能自己收款跳转），这会反过来约束 R-3 的计费设计。别先写好后端再发现要改。
