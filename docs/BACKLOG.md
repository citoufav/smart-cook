## B-1 · 多套库存（不同地点各存一份）✅ 已完成 2026-11-01

**日期**：2026-10-29 ｜ **来源**：用户实际使用后发现

**现状**：全应用只有一套食材/调料数据（`@v1:inventory:ingredients` / `@v1:inventory:seasonings`），跨设备、跨地点都不共享，也无法在设备上切换。

**用户原话**：*"有时候我要在不同地方做菜，库存不通用，虽然绝大多数场景一个都够用，但只能存一套库存还是有点不方便。"*

**定下来的方向**：单机多套库存档案（「家里」「单位」…），不做多设备同步 —— 同步要后端，和「无后端、BYOK」的定位冲突。

**实现（2026-11-01）**

- `src/services/inventoryProfileService.ts`：档案清单（`@v1:inventory:profiles`，一个 key 装列表+当前 id，保证原子），库存数据按档案分 key（`@v1:inventory:<profileId>:ingredients`）
- **迁移**：先写新 key → 读回来核对 → 再写档案指针。中途失败下次启动重跑；老 key 永不删除。校验失败也照样写指针（不然应用没法工作），但老数据一个字不动
- `ingredientService` / `seasoningService` 每次操作现问当前档案，不再碰常量 key
- `InventoryContext` 先定档案再读库存（顺序反了会读到上一个档案的数据）；切档案后重新 `loadData`
- 右上角 `InventoryProfileChip` + `InventoryProfileSheet`：当前档案打勾、其余可切、底部「再加一个」。默认只有「家里」，名字最多 12 字、最多 10 个档案
- `HeaderBar` 加了 `right` 插槽；标题改成绝对定位居中，右上角放东西也不会把「随煮」挤歪

**刻意没做**：删除/重命名档案。删除要处理"里面还有食材"，改名要让用户理解"那是在改档案不是在改菜"。等真的被烦到再加。

**只有库存分档案**：我的菜、已完成菜单、最近吃过、口味设置都**不跟地点走** —— 菜谱是跟人走的记忆，不是某个厨房的属性。所以界面上所有措辞都是「库存档案」，不是「切换档案」。

## B-3 · 菜品库：按菜存 + 生成时勾选 ⬜

**日期**：2026-10-30 ｜ **来源**：用户提出并确认方向

**为什么要改**：现在按「一次生成」存菜单，而菜单是一次性的；真正有复用价值的是**菜**。用户原话大意：*"完成的菜谱不按生成存，按菜存……跟一个个小卡片一样，想吃哪道菜了就点卡片看，而不是还要去历史里翻。"*

**已定的决策**：

| 项 | 决定 |
|---|---|
| 菜单历史副本 | **已删**（2026-10-30）。现在只剩 `cookingProgressService` 一份记录 |
| 菜的身份规则 | **A：同名归一化后覆盖**。`番茄炒蛋` = `番茄炒蛋 ` 视为同一道，库永远是最新版本，`timesCooked` 累加。**代价：旧配方不保留。** 若要保留历史版本需改成"同名不同配方算新菜" |
| 入库时机 | 做完菜时**自动入库**，可手动删 |
| 草稿（中途退出续做） | **已有**，就是做菜首页的「进行中的菜单」，不用新做 |

**分两期：**

### P3 · 生成时勾选 ✅ 已完成（2026-11-02）

```
选人数/热量/餐类 → [可选] 从我的菜勾任意道
  → 一次 AI 调用：给它已选菜的「菜名/几人份/热量/食材克数/调料」
  → 它返回 reused[{name, scale}] + 只补缺的菜（可以是空数组）
  → 本地按每道菜的倍数缩放（prepareReusedDishes），库存标记按当前库存重刷
  → 合并走 applyEdits 的 add_dish + 重算营养/缺料/采购清单
```

**关键决定：倍数交给 AI 拍，不设区间。** 用户原话：*"不设置什么区间上限吧，让AI自己决定吧……设置上限反而限制了AI发挥，限制主要是防止输出不合理得意外值，这个单独考虑吧，不要在生成的时候加这种限制了。"* 所以提示词里只写"家用炒锅塞不下就翻倍加菜"，倍数本身没有上下限；本地 `sanitizeScale` 只拦非数字/负数/10 倍以上（把克数当倍数写的意外值），退回「新人数 ÷ 当年人数」。

**同理不限勾选条数、不限补菜道数**：勾满一桌就是"这次不想要新菜"，是正常诉求。

**为什么不用人数比当倍数**：三个人吃一道菜不等于这道菜做三倍。家用炒锅塞不下 450g 肉丝，翻不开就变成煮菜；真实做法是加菜。所以是「每道菜一个倍数 + 由 AI 决定补几道」。

**已知取舍**：

- 库里的菜是「上次那版」：这次说"想吃辣"不会作用到勾选的旧菜，AI 只对它现补的菜生效
- 采购清单不信 AI，本地按当前库存重刷 `isInInventory` 后由 `applyEdits` 重算（旧菜存的那份库存标记早过期了）
- 热量更能差：已选菜只能缩不能换，剩余热量全靠补的菜去凑，差 10~15% 正常
- 主食不进库（见 P2），所以复用路径下米饭一类永远由 AI 现补 —— 这反而对，主食本来就该按人数重定
- **`basePersonCount` 只存"最近一次"**：同一道菜做过 2 人份又做过 4 人份，存后者
- 跨菜顺序：AI 的 summary 不覆盖旧菜，备菜/炒制页按菜的先后展示，不重排

# 路线图（R-*）

远期功能与它们对现有代码的要求。**只记需求与影响面，不预先写代码**——真正做的时候按当时的代码再定实现。顺序大致按「无后端 → 有后端」排。

## R-1 · 多语言系统（i18n）⬜

**现状**：零预留。72 个源文件里 46 个含中文，约 580 行（含注释，纯 UI 文案粗估 300~400 条），全部硬编码在 JSX 里。

**三处要改，难度递增**：

1. **UI 文案**——抽 `t()` + 语言包。工作量在这块（46 个文件），但机械。
2. **AI 输出语言**——`aiService.ts:216` 的 `18. 所有输出使用中文` 写死在 system prompt 里。改成变参。
3. **prompt 骨架**——`SYSTEM_PROMPT_CN` 整段是中文，且含中餐专属规则（`中餐为主，1人份主料150-300g`）。要按语言拆模板。

**语言存哪**：`UserPreferences.locale` —— **字段已于 2026-10-30 预留，值是 `'zh-CN'`**，目前无人读取。

**注意**：语言和服务端无关，纯前端就能做完。但语言包里的菜名、调料名会被写进库存和 AI 输出，**切换语言后已有数据不会翻译**——要么接受混合，要么只对新数据生效。这点先想清楚再动手。

## R-2 · 多国家菜系支持 ⬜

**现状**：`SYSTEM_PROMPT_CN` 第 10 条写死中餐；`tastePreferences: string[]` 是自由字符串（开屏页选的川菜/清淡之类），AI 按字符串理解，没有菜系 id 概念。

**要引入一个 `cuisine` 维度**：菜系 id + 显示名 + prompt 片段 + **单位体系**。

单位是坑：克重在中餐里通用，但西餐写 `cup`/`oz`、日料写 `大さじ`。这不只是换算，是表达习惯——硬转成克会让菜谱读起来别扭。`buildStage1UserPrompt` 里的「克」和系统 prompt 里的「Xg」格式都要跟着菜系走。

**和 R-1 是同一处改动**：`UserPreferences.cuisineIds: string[]`（**2026-10-30 已预留，目前恒为空**），prompt 模板化时一起做。分开做两次是浪费。

## R-4 · 图片识别食材记录 ⬜

**现状**：无相机/相册依赖。`expo-document-picker` 只用于导入库存 JSON。

**要什么**：

- `expo-image-picker`（相机 + 相册，含权限弹窗）
- 多模态调用——**已确认可行，不用换供应商**：官方 `deepseek-flash`（DeepSeek-V4.1-Flash-1017）的 `input_modalities` 是 `["text","image"]`，`deepseek-v4-pro` 只有 `["text"]`。所以只要把模型切到 flash 就能发图，不需要走 R-3 的云端代理。（2026-10-30 更正：此前记的"DeepSeek 无视觉能力"是错的）
- 识别结果确认界面——**可复用 `cooking/inventory-update.tsx` 的批量勾选确认模式**，那块已经有「建议 vs 当前」的对照 UI

**对架构无要求**：纯新增一个 service 函数 + 一个页面，不挡路。放后台做。

## R-5 · 食物过期提醒 ⬜

**现状**：`Ingredient` 只有 `createDate`。AI 是靠「已存放 N 天」（`aiService.ts:232`）自己猜新鲜度的，没有保质期概念。

**要什么**：

1. `Ingredient.expireDate?: string`（**2026-10-30 已加进类型和 service，暂无 UI**）
2. **品类 → 默认保质期映射**：肉 3 天 / 叶菜 5 天 / 蛋 21 天 / 冷冻 90 天。这个表要能调，不同存储条件（冷藏/冷冻/常温）差别很大
3. `expo-notifications` 本地通知 + 通知权限
4. 库存页的临期排序/标红

**这是唯一一个「现在加字段比以后加便宜」的功能**：一旦用户有一批没 `expireDate` 的数据，补录要一条条填。字段现在加、UI 以后做，成本是 0。

## R-6 · 云端账户同步（食材 + 记录）⬜

**现状**：10 个存储 key 全是扁平的 `@v1:xxx`（`src/constants/storageKeys.ts`），没有 userId 概念。「这台设备的数据」这个假设渗透在全部读写路径里。

**为什么最难**：不是「换个存储后端」，而是引入**「两份数据可能不一致」这个新状态**，然后要回答：

- 两台设备同时改库存，谁赢？（last-write-wins 会丢数据，CRDT 要重构整个数据模型）
- 离线改了，上线后怎么合？
- 删除怎么传播？（没有墓碑的同步会把删掉的食材「复活」）

**预留缝**：存储 key 加命名空间 `@v1:u:<userId>:inventory:ingredients`。**改起来只在 `storageKeys.ts` 一个文件**，但错过就要写数据迁移。

**判断**：现在**不改**。等 R-6 真做时一起改，届时用户量小（可能就你自己），迁移成本≈0。记在这里是因为「改法只有一种」，别忘了。

**和 B-1 的关系**：B-1（多套库存）和本地多档案是同一层命名空间问题，做 B-1 时顺手设计，别做两遍。

## R-7 · 会员 ⬜

**现状**：无账号、无支付、无后端。

**链条**：账号 → 订阅状态 → 额度（AI 调用次数 / 图片识别次数）→ 支付（App Store / Play 内购，抽成 15~30%）。

**硬前提是 R-3**：没有云端代理就没有可计量的「用量」，会员没东西可卖。所以 R-7 必然排在 R-3 之后。

**注意应用商店规则**：iOS 上卖数字服务必须走内购（不能自己收款跳转），这会反过来约束 R-3 的计费设计。别先写好后端再发现要改。
