# SmartCook 数据与状态管理现状分析 & 重构方案

> 本文档梳理当前代码中「数据模型 + 状态管理」的真实状况，定位混乱根源，并给出重构方案。
> 面向：项目作者本人，用于在动手重构前对齐方向。

---

## 一、当前架构总览

### 1.1 Provider 层级（`app/_layout.tsx`）

```
SafeAreaProvider
└─ SettingsProvider      # 设置/偏好/API Key
   └─ InventoryProvider  # 库存（食材 + 调料）
      └─ CookingProvider # 做菜会话（核心）
         └─ NutritionProvider     # 营养数据展示
            └─ CustomAlertProvider
               └─ ChatBallProvider    # 聊天悬浮球 UI 状态
                  └─ ChatSheetProvider # 聊天面板 UI 状态
                     └─ SettingsDrawerProvider
                        └─ AppContent
```

共 **7 个 Context**，职责如下：

| Context | 职责 | 状态容器 |
|---------|------|---------|
| SettingsContext | API Key、模型、忌口、做菜默认值 | useReducer |
| InventoryContext | 食材/调料 CRUD + 导入导出 | useReducer |
| CookingContext | 做菜会话、阶段推进、菜单方案 | useReducer |
| NutritionContext | 营养数据、悬浮球显示 | useReducer |
| ChatBallContext | 聊天球显隐 + 点击回调 | useState + ref |
| ChatSheetContext | 聊天面板显隐 + 菜谱上下文 | useState |
| SettingsDrawerContext | 设置抽屉显隐 | useState |

### 1.2 分层

```
app/ 页面 → src/components UI → src/contexts 状态 → src/services 业务/持久化 → src/utils 纯函数
```

名义上分层清晰，但**页面层有多处直接绕过 context 调用 service**（见问题 4），破坏了这条链路。

## 二、核心数据模型

### 2.1 做菜会话（`CookingSession`）

```
CookingSession
├── id
├── status            # CookingStage（当前阶段）
├── completedStageIndex  # 已完成进度索引
├── stages
│   ├── requirement    # RequirementInput
│   ├── menu           # Stage1Data { menuProposal, requirementInput, reasoningContent }
│   └── generatedPlan  # GeneratedPlan { prepSteps, cookingSteps, preciseNutrition }
└── version / createdAt / updatedAt
```

### 2.2 菜单方案（`MenuProposal`）与生成方案（`GeneratedPlan`）

```ts
// MenuProposal（types/index.ts L109）
interface MenuProposal {
  dishes: DishPlan[];
  estimatedNutrition: NutritionInfo;
  missingItems: ShoppingItem[];
  cookingOrderDescription: string;
  flavorDescription: string;
  summary: MenuSummary;
  prepSteps?: PrepStep[];        // ⚠️ 已包含
  cookingSteps?: CookingStep[];  // ⚠️ 已包含
  preciseNutrition?: NutritionInfo[];  // ⚠️ 已包含
}

// GeneratedPlan（types/index.ts L173）
interface GeneratedPlan {
  prepSteps: PrepStep[];         // ⚠️ 重复！
  bowlAssignments?: BowlAssignment[];
  cookingSteps: CookingStep[];   // ⚠️ 重复！
  preciseNutrition: NutritionInfo[];  // ⚠️ 重复！
  ingredientTags?: IngredientTag[];
}
```

**这是当前最核心的问题：`prepSteps` / `cookingSteps` / `preciseNutrition` 同时存在于 `MenuProposal` 和 `GeneratedPlan` 两个地方。**

## 三、问题清单（按严重程度排序）

### 🔴 问题 1：数据双份存储，无单一真相源（最根本）

`prepSteps`、`cookingSteps`、`preciseNutrition` 同时存在两份：

- `stages.menu.menuProposal.prepSteps`
- `stages.generatedPlan.prepSteps`

导致 [CookingContext.tsx](file:///e:/program/trae/SmartCook/SmartCook_demo/src/contexts/CookingContext.tsx) 里：

- `SET_STAGE1_RESULT`（L131-154）要同时写 `menu.menuProposal` 和 `generatedPlan`
- `UPDATE_PLAN`（L156-175）要同时同步两份
- `RESTORE_SESSION`（L80-101）甚至要从 `menu.menuProposal` 重建丢失的 `generatedPlan`

改一处忘同步另一处，就是状态不一致 bug 的温床。UI 层也因此无所适从，例如 [CookingPager.tsx](file:///e:/program/trae/SmartCook/SmartCook_demo/src/components/CookingPager.tsx#L115-L124) 里要写 `genPlan?.prepSteps || mp?.prepSteps` 这种双来源兜底。

### 🔴 问题 2：AI 改菜谱链路脆弱（ChatSheet）

[ChatSheet.tsx](file:///e:/program/trae/SmartCook/SmartCook_demo/src/components/ChatSheet.tsx#L171-L364) 的 `executeToolCalls` 是重灾区：

1. `JSON.parse(JSON.stringify(...))` 深拷贝出 **4 个数组**（`prepSteps`、`cookingSteps`、`gpPrepSteps`、`gpCookingSteps`）
2. `update_step` 要同时遍历 4 个数组，且 `description` 和 `instruction` 都赋值（因为不确定步骤是备菜还是炒制）
3. 改完后：手动拼 `updatedSession` → `cookingProgressService.save()`，与 `dispatch(UPDATE_PLAN)` 是**两份重复的更新逻辑**

这是「AI 生成菜谱 + AI 对话改菜谱一片混乱」的直接来源。

### 🟡 问题 3：历史遗留死代码污染类型系统

- `CookingStage` 类型（types/index.ts L222-231）仍含 `weighing`、`bowl` 两个已废弃阶段，但 `STAGE_KEYS = ['menu', 'prep', 'cooking']` 已不用它们
- 一整套旧「称量/分装」流程类型全部死亡但仍在：`WeighingData`、`BowlAssignment`、`Stage2Data`、`Stage2AIInput`、`Stage2AIResponse`、`Stage2Progress`、`ShoppingListProgress`、`ExecutionProgress`
- [stage1-menu.tsx](file:///e:/program/trae/SmartCook/SmartCook_demo/app/cooking/stage1-menu.tsx) 里 `Stage1MenuScreen`（Default 导出）和 `Stage1MenuContent`（命名导出）**约 80% 代码重复**，且 Default 版本里还残留 `setCurrentStage('weighing')` + `router.push('/cooking/stage2-weighing')` 跳转到已删除页面的死代码（L55-58）
- [storageKeys.ts](file:///e:/program/trae/SmartCook/SmartCook_demo/src/constants/storageKeys.ts) 里多个 key 已无对应使用：`COOKING_SESSION_ACTIVE`、`STAGE2_PROGRESS`、`EXECUTION_PROGRESS`、`SHOPPING_LIST_ACTIVE`、`UNDO_SNAPSHOT`

### 🟡 问题 4：历史记录两套系统并存 + 页面绕过 context

存在**两套**做菜历史：

1. `menuHistoryService`（`@v1:cooking:session:history`）—— 存 `MenuHistoryItem`，含完整 `menuProposal`
2. `cookingProgressService`（`@v1:cooking:progress_records`）—— 存 `CookingProgressRecord`，含完整 `session`（里面又有 `menuProposal`）

两者都存了菜单数据的完整副本，且在 [cooking.tsx](file:///e:/program/trae/SmartCook/SmartCook_demo/app/(tabs)/cooking.tsx#L199-L355) 的 `handleStreamDone` 里被**同时写入**（还各构造了一份 `menuProposal` 对象）。

同时，历史页 [history/index.tsx](file:///e:/program/trae/SmartCook/SmartCook_demo/app/history/index.tsx) 和 [history/[id].tsx](file:///e:/program/trae/SmartCook/SmartCook_demo/app/history/[id].tsx) 直接调用 `menuHistoryService` + `useState`，**完全绕过 context**，与做菜会话的数据流割裂。

### 🟡 问题 5：`handleStreamDone` 里 menuProposal 被重复构造 3 次

[cooking.tsx](file:///e:/program/trae/SmartCook/SmartCook_demo/app/(tabs)/cooking.tsx#L199-L355) 里，同一份 `menuProposal` 对象被手写构造了 **3 次**：

1. `setStage1Result` 里（L227-245）
2. `menuHistoryService.add` 里（L286-296）
3. `cookingProgressService.save` 里（L313-334）

字段一旦增加，要改 3 处，极易漏改。

### 🟢 问题 6：阶段模型的语义已经退化

从 5 阶段简化为 3 阶段后，[CookingPager.tsx](file:///e:/program/trae/SmartCook/SmartCook_demo/src/components/CookingPager.tsx#L112) 里所有 stage 都硬编码 `mode: 'readonly'`，`completedStageIndex` 的三状态模型（locked/readonly/interactive）实际已不再使用，但相关代码（`useStageMode`、`getStageMode`、`ensureCompletedStageIndex` 迁移逻辑）都还留着，增加了理解成本。

## 四、重构目标

1. **确立单一真相源**：菜单方案只有一份，消除 `MenuProposal` 与 `GeneratedPlan` 的重复。
2. **AI 改菜谱抽成纯函数**：把改菜谱逻辑从组件里抽离为可测试的纯函数。
3. **清理死代码**：删除 weighing/bowl 相关类型、字段、重复组件、废弃 storageKey。
4. **收敛历史记录**：明确 menu history 与 cooking progress 的边界，消除重复写入。
5. **页面接入 context**：历史页改为通过 context 读取，统一数据流。

**不引入新依赖、不换状态库。** 继续用 React Context + useReducer，只是把数据模型和职责边界理清。这是最小、最稳的重构。

## 五、重构方案（分阶段）

### 阶段 A：确立单一真相源（核心）

**目标**：`prepSteps`/`cookingSteps`/`preciseNutrition` 只存一份，放在 `MenuProposal` 里；`generatedPlan` 要么删除，要么退化为只存「AI 原始输出」的派生缓存。

**具体**：
1. 从 `CookingSessionStages` 里删除 `generatedPlan`（或改为只读派生字段）
2. `SET_STAGE1_RESULT` / `UPDATE_PLAN` / `RESTORE_SESSION` 只操作 `menu.menuProposal`
3. `CookingPager` 的 `recipeContext`、`ChatSheet`、`history/[id]` 统一从 `menuProposal` 读步骤
4. 数据迁移：旧数据里 `generatedPlan` 的值回填到 `menuProposal`（已有 `RESTORE_SESSION` 的重建逻辑可复用）

### 阶段 B：抽纯函数 `applyRecipeChanges`

**目标**：把 [ChatSheet.tsx](file:///e:/program/trae/SmartCook/SmartCook_demo/src/components/ChatSheet.tsx) 里 `executeToolCalls` 的 300 行深拷贝 + 4 数组同步逻辑，抽成：

```ts
// src/services/recipeEditService.ts（或 utils）
applyRecipeChanges(menuProposal: MenuProposal, changes: RecipeChange[]): MenuProposal
```

纯函数，输入旧方案 + 变更列表，输出新方案。组件里只做两件事：
1. `const next = applyRecipeChanges(current, changes)`
2. `dispatch(UPDATE_PLAN, next)` + `persist(next)`

这样改菜谱逻辑可单测、可复用，不再有深拷贝和 4 数组手动同步。

### 阶段 C：清理死代码

1. `types/index.ts`：删除 `WeighingData`、`BowlAssignment`、`Stage2Data`、`Stage2AIInput`、`Stage2AIResponse`、`Stage2Progress`、`ShoppingListProgress`、`ExecutionProgress`；`CookingStage` 里删 `weighing`/`bowl`
2. `constants/cooking.ts`：`VALID_TRANSITIONS` 删掉 weighing/bowl 相关（已是 3 阶段，确认无遗漏）
3. `constants/storageKeys.ts`：删 `COOKING_SESSION_ACTIVE`、`STAGE2_PROGRESS`、`EXECUTION_PROGRESS`、`SHOPPING_LIST_ACTIVE`、`UNDO_SNAPSHOT`
4. `stage1-menu.tsx`：删除重复的 `Stage1MenuScreen`（Default 导出）和其中死代码，只保留 `Stage1MenuContent`
5. 删除 `src/utils/bowlValidation.ts`（若已无引用）
6. `inventoryCalculator.ts` 里的 `Stage2AIInput` 引用（若已被阶段 A 影响，一并清理）

### 阶段 D：收敛历史记录

1. 明确分工：
   - `menuHistoryService` → 只存「菜单方案历史」（供历史列表/详情展示）
   - `cookingProgressService` → 只存「做菜进度/断点续做」
2. 消除 `handleStreamDone` 里 `menuProposal` 的 3 次重复构造：先构造一次，复用到 3 处
3. 历史页 `history/index.tsx`、`history/[id].tsx` 改为通过 context（新增 `MenuHistoryContext`，或复用现有 service + 统一 hook）读取，不再各自 `useState` + 直接调 service

### 阶段 E（可选）：清理退化阶段模型

若确认「readonly 三阶段」是最终形态，可：
1. 删除 `useStageMode`/`getStageMode`/`StageMode` 三状态模型
2. 删除 `completedStageIndex`（改用 `status` 单值）
3. 简化 `ensureCompletedStageIndex` 迁移逻辑

这一步收益较低、改动面较大，**建议放到最后、且单独评估**。

## 六、建议实施顺序

| 顺序 | 阶段 | 收益 | 风险 |
|------|------|------|------|
| 1 | A 单一真相源 | 高（治本） | 中（涉及数据迁移） |
| 2 | B 抽纯函数 | 高（改菜谱清晰） | 低 |
| 3 | C 清死代码 | 中（可读性） | 低 |
| 4 | D 收敛历史 | 中（数据流统一） | 中 |
| 5 | E 清退化模型 | 低 | 中，建议单独评估 |

**A → B 是核心，做完即可明显改善「AI 生成 + 对话改菜谱」的混乱。**

## 七、验证方式

每完成一个阶段，用以下方式验证不回归：

1. `npx tsc --noEmit` 无新增类型错误
2. 完整走一遍：录入库存 → AI 生成菜单 → 查看 3 阶段 → AI 对话改菜谱 → 完成做菜 → 历史记录查看
3. 重点回归：改菜谱后，菜谱页/备菜页/炒制页/历史详情页的步骤是否一致（旧数据兼容）
